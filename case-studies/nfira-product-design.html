Designing the NFIRA CRE System

From a manual follow-up workbook to a coordinated CRM system, with a clear boundary between automation and human relationships.

Sole product designer and systems ownerNFI SolutionsDecember 2025 to present

The Client Relationship Expert (CRE) is the staff member who operates the NFIRA CRE System. This page covers product evolution; the UI/UX study covers the staff and client interfaces. Screenshots use test data and internal reference names, with staff last names obscured.

The brief

The founder wanted a system that could track client engagement and support email and messaging while preserving a human voice. Automation needed to organize the work without taking over the relationship.

My role was to define that boundary and build a system around it, from an interim manual tracker to the CRE Automation Engine.

The problem

NFIRA runs recurring client seminars, approximately 12 a year. One Client Relationship Expert (CRE) was responsible for follow-up and appointment reminders. Each attendee could move into a different path depending on attendance, booking, and subsequent outcomes.

There was no shared system to hold the current state of those relationships. The design problem was to make that state reliable and show the CRE what needed to happen next.

v0: A manual bridge

The CRE needed something usable before the automation was ready. I built a multi-tab Excel workbook with an individual guide for each client and an automatically populated follow-up list.

Each guide showed a CURRENT row for the next unfinished action. Inactive paths grayed out, while a path-change log recorded transitions and their reasons. The workbook calculated dates and flagged overdue work; the CRE still chose the path, recorded progress, and performed every outreach action.

Where the tracker broke down

As the caseload grew, updating the tracker became another job alongside outreach. The CRE began keeping separate informal notes, weakening the shared record the workbook was meant to provide.

My own test scenario exposed a second weakness. A client missed an appointment, entered recovery, then rescheduled. The static dates and path history made it difficult to distinguish previous activity from the current state.

That finding shaped the next version: the system needed to maintain an explicit current state, not simply accumulate history.

More of the interim workbook

v1: One workflow reaches its limit

The first HubSpot version branched on NFIRA Journey Stage and updated status properties. This was sufficient while the job was mainly keeping a small set of fields aligned.

Adding cadence messages and tasks changed the problem. The system now needed to check suppression, select a follow-up path, and coordinate workflows over time. I moved from one branching workflow to a router with specialized workflows.

v2: Separate routing from outreach

WF-00, the Master Path Router, evaluates contact properties and decides which workflow should handle the contact next. It does not send cadence messages.

The priority is explicit: check hard exits and suppression first, then deferral, then the seminar and appointment paths. Path branches check suppression again before assigning an active cadence.

Keep suppression in control

An early routing conflict could undo a suppression. WF-90 would suppress a contact, but a later WF-00 run could recognize their attendance and put them back into an active path.

I addressed this by requiring each path branch to check Suppression/Exit before setting a cadence. Suppression became a prerequisite for routing, rather than a status the router could overlook.

Recognize returning clients

Someone booking again after no-show recovery has a different history from a first-time booking. A returning branch checks Cadence Day/Step, records a note, and hands the contact to WF-01, Appointment Protection.

The design preserves that context instead of treating every booking as a new entry.

Allow more than one route to nurture

Contacts can enter Long-Term Nurture after completing Path 2 without converting, or directly when their outcome is “Declined – Nurture Okay.” The system supports both situations without requiring everyone to complete the same cadence first.

Additional routing branches

Re-engage without duplicating decisions

WF-11 handles clients whose requested pause has ended. It updates re-engagement and cadence status, clears the follow-up request, and returns the contact to WF-00.

The same rule applies throughout: supporting workflows update state; the master router decides which path comes next. This keeps routing decisions in one place.

Deferred re-engagement overview

A structured entry point

The import workbook separates seminar setup, attendee entry, and generated HubSpot output. Staff enter the shared seminar details once, then record what happened for each attendee.

The generated sheet provides a routing preview and import checks before the data enters HubSpot. This connects the operational record to the state model the automation relies on.

CRE v1 automates through the first appointment. After that, the relationship becomes primarily human-led.

Set a deliberate boundary

The scope returns to the founder’s brief. The system supports the first appointment through reminders and recovery, while subsequent conversations require staff judgment and personal follow-up.

That boundary was a product decision about the role of automation, rather than a reason to automate every technically possible interaction.

Where this stands

The CRE Automation Engine is live but new. There is not yet outcome data to quantify its impact. It supports the CRE by tracking client state and coordinating follow-up workflows, while the CRE operates the system and handles the human-led work.

The next evaluation should measure time spent tracking clients separately from time spent on outreach, and whether contacts move through their expected paths on schedule.

What I would improve

I would make changing client states more visually distinct in the initial workbook, using the recovery-and-rebooking scenario as an early design test.

I would also instrument workflow timing from the start, including suppression checks and time in each cadence step. That would give future assessments a measured basis.
